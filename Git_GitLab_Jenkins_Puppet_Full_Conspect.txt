1. SETUP & CONFIGURATION
================================================================================

git --version
    Print installed Git version. First sanity check after install.

git config --global user.name "Your Name"
    Set the name attached to every commit you make. Global = all repos on this
    machine.

git config --global user.email "you@example.com"
    Set the email attached to every commit. Must match GitLab account email
    for commits to show as "yours" on GitLab.

git config --global init.defaultBranch main
    Make new repos start with branch "main" instead of "master".

git config --global core.editor "code --wait"
    Set VS Code as the editor Git opens for commit messages, rebase TODOs, etc.
    --wait makes Git wait until you close the editor.

git config --global core.editor "notepad"
    Same idea, but use Notepad. Simpler if VS Code isn't installed.

git config --global pull.rebase true
    When you "git pull", rebase your local commits on top of remote instead
    of creating a merge commit. Cleaner history.

git config --global pull.rebase false
    Opposite — pull always merges. Classic behaviour.

git config --global pull.ff only
    Refuse to pull if it would require a merge or rebase. Forces you to
    decide explicitly. Safest option.

git config --global --list
    Show all global config values.

git config --global --get-regexp alias
    List all your aliases.

git config --global alias.st "status"
    Make "git st" a shortcut for "git status".

git config --global alias.lg "log --oneline --decorate --graph --all"
    Make "git lg" the pretty graph log. Most useful alias you'll set.

git config --global alias.last "log -1 --stat"
    Make "git last" show the most recent commit with file stats.

2. SSH KEY (FOR GITLAB)
================================================================================

ssh-keygen -t ed25519 -C "you@example.com"
    Generate a new SSH key pair (modern algorithm). Press Enter to accept
    default path ~/.ssh/id_ed25519. Add a passphrase for extra security.

eval "$(ssh-agent -s)"
    Start the SSH agent in your current Bash session. The agent holds your
    decrypted key in memory so you don't retype the passphrase every time.

ssh-add ~/.ssh/id_ed25519
    Load your private key into the agent.

cat ~/.ssh/id_ed25519.pub
    Print your PUBLIC key. Copy this and paste into GitLab → Edit Profile →
    SSH Keys. NEVER share the file without .pub at the end.

ssh -T git@gitlab.com
    Test the connection to GitLab over SSH. Expected output: a welcome
    message with your username. If it fails, the public key isn't in GitLab
    or the agent isn't running.

3. CREATING & CLONING REPOS
================================================================================

git init
    Turn the current folder into a Git repo. Creates a hidden .git/ folder.

git clone <url>
    Download a remote repo to your machine. Creates a folder named after the
    repo. Sets the source as remote "origin" automatically.

git clone git@gitlab.com:user/project.git
    Clone via SSH. Requires SSH key to be set up.

git clone https://gitlab.com/user/project.git
    Clone via HTTPS. Will ask for username/Personal Access Token (NOT your
    account password — GitLab disabled that).

mkdir -p <folder> && cd <folder>
    Make a folder (and parent folders if missing) and enter it. The -p means
    "no error if it already exists".


================================================================================
4. BASIC WORKFLOW (THE BIG FOUR)
================================================================================

git status
    Show what's changed, what's staged, what's untracked, and which branch
    you're on. Run this constantly. When confused, run this.

git add <file>
    Stage a specific file for the next commit.

git add .
    Stage everything in the current folder (modified + new). Most common.

git add -p
    Interactive staging — Git shows you each "hunk" (chunk of changes) and
    asks y/n/s/q. Use this to split a big edit into multiple clean commits.
    Keys:
        y = stage this hunk
        n = skip this hunk
        s = split a big hunk into smaller pieces
        q = quit

git commit -m "message"
    Create a commit from staged changes with the given message.

git commit -am "message"
    Stage all MODIFIED tracked files AND commit, in one step. Does NOT add
    new untracked files — you still need git add for those.

git commit --amend -m "new message"
    Replace the LAST commit with a new one. Use to fix a typo in the message
    or to add forgotten files (stage them first, then --amend).
    DANGER: don't amend commits that are already pushed to a shared branch.

git push
    Send commits from your current branch to its tracked remote branch.

git push -u origin <branch>
    First-time push of a new branch. -u sets the "upstream" link so future
    pushes/pulls know where to go. After this, plain "git push" works.

git pull
    Fetch from remote AND merge (or rebase, depending on config) into your
    current branch.

git pull --ff-only
    Pull only if the result is a fast-forward (no merge needed). Refuses
    otherwise. Safest pull — forces you to handle divergence explicitly.

git fetch
    Download remote commits into your local copy WITHOUT merging them. Use
    when you want to see what's new before deciding what to do.

git fetch upstream
    Same, but from the "upstream" remote (used in fork workflow).


================================================================================
5. INSPECTING HISTORY
================================================================================

git log
    Full commit history, newest first. Verbose.

git log --oneline
    One commit per line: short SHA + commit message.

git log --oneline --decorate --graph --all
    THE useful log view. Shows:
        --oneline   = compact
        --decorate  = branch/tag names next to commits
        --graph     = ASCII art of branches/merges
        --all       = include all branches, not just current
    Aliased as "git lg" in most setups.

git log --stat
    Show file changes per commit (which files, how many lines added/removed).

git log -1
    Show only the most recent commit.

git log -- <path>
    History of one specific file. Note the "--" — it separates paths from
    refs so Git doesn't get confused.

git log --merges
    Show only merge commits.

git show <commit-hash>
    Full diff of one specific commit (what changed in that commit).

git show HEAD
    Show the most recent commit on your current branch.

git show v0.1.1
    Show what a tag points to (and the tag's annotation if it's annotated).

git diff
    Show UNSTAGED changes (working tree vs index).

git diff --staged
    Show STAGED changes (index vs last commit). Same as --cached.

git diff HEAD
    Show ALL changes (staged + unstaged) compared to last commit.

git diff <branch1>..<branch2>
    Show all changes between two branches (see Section 11 for range syntax).

git reflog
    Log of every move HEAD has made — switches, commits, resets, rebases.
    Local only, never pushed. Your "undo of last resort" — if you lost a
    commit, find its SHA here and recover it.

git reflog --date=iso
    Same, but with full ISO timestamps.

git branch -vv
    List local branches with their tracked remote branch and ahead/behind
    counts. The double -v shows tracking info.

git remote -v
    List remotes with URLs. Verifies origin and upstream are set right.


================================================================================
6. BRANCHES
================================================================================

git branch
    List local branches. The current one has a *.

git branch -a
    List local AND remote branches.

git switch <branch>
    Move to an existing branch. Modern command (replaces "git checkout").

git switch -c <new-branch>
    Create a new branch from the current commit AND switch to it.

git switch -c <new-branch> <starting-point>
    Create a new branch starting from a specific commit/branch/tag, then
    switch to it. Useful for branching off a tag or old commit.

git switch main
    Go back to main.

git switch -                        (with a literal dash)
    Switch to the previously checked-out branch. Like "cd -" in bash.

git checkout <branch>
    Older equivalent of git switch. Still works, still in every tutorial.

git checkout -b <new-branch>
    Older equivalent of git switch -c.

git branch -d <branch>
    Delete a branch SAFELY (refuses if it has unmerged commits).

git branch -D <branch>
    Delete a branch FORCEFULLY (even if unmerged). Use with care.

git push origin --delete <branch>
    Delete a branch on the remote.


================================================================================
7. MERGING
================================================================================

git merge <branch>
    Merge <branch> INTO your current branch. If main has moved since the
    feature branch split, this creates a merge commit.

git merge --ff-only <branch>
    Merge only if it can fast-forward (no merge commit needed). Refuses
    otherwise.

git merge --no-ff <branch>
    Force a merge commit even when fast-forward is possible. Preserves the
    fact that a feature branch existed.

git merge -s octopus branch1 branch2
    Merge MULTIPLE branches into one merge commit. Only works if there are
    no conflicts. Used to demonstrate merge with multiple parents.

git merge --abort
    Cancel a merge in progress (e.g., when you hit a conflict and want out).

CONFLICT RESOLUTION:
    When git merge fails with conflicts, opened files contain markers:

        <<<<<<< HEAD
        your version (current branch)
        =======
        their version (incoming branch)
        >>>>>>> feature/x

    Edit the file, remove all <<<<<<<, =======, >>>>>>> markers, keep what
    you want, then:

        git add <file>
        git commit          # completes the merge with default message

git checkout --ours <file>
    During a conflict: keep YOUR version (the branch you were on when you
    started the merge). Then "git add <file>" and commit.

git checkout --theirs <file>
    During a conflict: keep the INCOMING version (the branch being merged in).
    Then "git add <file>" and commit.
    NOTE: in a rebase, "ours" and "theirs" SWAP meaning because rebase replays
    your commits onto the other branch — confusing but important.

git merge-base <branch1> <branch2>
    Print the SHA of the common ancestor of two branches. The point where
    they diverged. Useful for understanding what a merge will actually merge.


================================================================================
8. REBASE
================================================================================

git rebase <branch>
    Replay your branch's commits ON TOP OF <branch>. Rewrites SHAs.
    Result: linear history, no merge commit, but commits are technically
    new objects (new SHAs).

git rebase origin/main
    Common case: bring your feature branch up to date with main without a
    merge commit.

git rebase --continue
    After resolving a conflict during a rebase: stage the fixed file with
    "git add", then continue the rebase.

git rebase --abort
    Cancel a rebase in progress, return to where you started.

git rebase --skip
    Skip the current commit during rebase (you're saying "this commit's
    changes shouldn't be applied"). Rare.

git rebase -i <commit>
    Interactive rebase. Opens an editor where you can reorder, squash, drop,
    reword commits since <commit>. Powerful but only for unpushed commits.

WHEN TO USE WHICH:
    - Rebase YOUR OWN feature branch BEFORE merging into main → clean linear
      history.
    - NEVER rebase main.
    - NEVER rebase a branch others are working on.
    - Merge is always safe, never rewrites history, but adds merge commits.


================================================================================
9. UNDOING THINGS (THE DECISION TREE)
================================================================================

git restore <file>
    Discard UNSTAGED changes in a file. Working tree is reset to match the
    index. Replaces older "git checkout -- <file>".

git restore --staged <file>
    UNSTAGE a file (move it from index back to working tree). The actual
    edits are kept. Replaces older "git reset HEAD <file>".

git restore --staged --worktree <file>
    Both unstage AND discard the change. Equivalent to running both
    --staged and plain restore.

git reset --soft HEAD~1
    Undo last commit, KEEP changes STAGED.

git reset --mixed HEAD~1            (default, same as just "git reset HEAD~1")
    Undo last commit, KEEP changes in working tree but UNSTAGED.

git reset --hard HEAD~1
    Undo last commit AND DELETE the changes. DESTRUCTIVE — no recovery
    except via reflog.

git reset --hard origin/main
    Force your local branch to exactly match origin/main. Used to throw
    away all local commits/changes.

git revert <commit>
    Create a NEW commit that inverts the given commit. SAFE for shared/
    pushed history because it doesn't rewrite anything.

git revert HEAD
    Revert the last commit.

git clean -n
    PREVIEW which untracked files would be deleted. Always run this first.

git clean -f
    Actually delete untracked files. -f required because it's destructive.

git clean -fd
    Also delete untracked directories.

git stash
    Save your current uncommitted changes (tracked files only) and revert
    the working tree to clean state. Like a clipboard for changes.

git stash push -m "message"
    Stash with a description. Highly recommended over plain "git stash".

git stash list
    Show all stashes. Each has a name like stash@{0}, stash@{1}, ...

git stash pop
    Apply the most recent stash AND remove it from the stash list.

git stash apply
    Apply the most recent stash but KEEP it in the stash list (in case you
    want to apply it again somewhere).

git stash drop stash@{N}
    Delete a specific stash without applying it.

git stash show -p stash@{N}
    Show the diff of a stash without applying it.


================================================================================
10. TAGS
================================================================================

git tag
    List all tags.

git tag v0.1
    Create a LIGHTWEIGHT tag. Just a name pointing at a commit. No metadata.

git tag -a v0.1.1 -m "First milestone"
    Create an ANNOTATED tag with tagger info, date, message. Use this for
    releases. Stored as a real Git object.

git tag -a v0.1.1 <commit-hash> -m "msg"
    Tag a specific past commit, not just HEAD.

git show v0.1.1
    Show the tag info AND the commit it points to.

git push origin v0.1.1
    Push a single tag to the remote (tags don't push by default!).

git push origin --tags
    Push ALL local tags to the remote.

git tag -d v0.1
    Delete a local tag.

git push origin --delete v0.1
    Delete a tag on the remote.

11. RANGE & REVISION SELECTION SYNTAX (THE CONFUSING PART)
================================================================================

This is the part that trips most students up on the exam.

HEAD
    The commit you're currently on (= the tip of your current branch).

HEAD~1                              (or HEAD^)
    The PARENT of HEAD (one commit back).

HEAD~2
    Two commits back.

HEAD~5
    Five commits back.

HEAD^ vs HEAD~
    For normal commits with one parent, HEAD~ and HEAD^ mean the same thing.
    For MERGE commits (which have two parents), they differ:
        HEAD^1  = first parent (the branch you were ON when merging)
        HEAD^2  = second parent (the branch you merged IN)
        HEAD~1  = HEAD^1 (always follows first-parent chain)

A..B  (TWO DOTS)
    "Commits reachable from B but NOT from A."
    In English: "what does B have that A doesn't?"

    Example: git log main..feature
        → commits on feature that aren't on main yet (= what your PR will add)

    Example: git log upstream/main..HEAD
        → commits on your branch that aren't yet on upstream's main
          (= what you would submit in an MR)

    Example: git diff main..feature
        → the total diff your feature would introduce

A...B  (THREE DOTS)
    "Commits reachable from EITHER A or B but NOT BOTH."
    In English: "what's diverged between them?"

    Example: git log main...feature
        → commits unique to main + commits unique to feature
          (= the symmetric difference)

    Used less often than two-dot. Mostly for "show me all the divergence".

A^!  (A and a bang)
    Just commit A and nothing else. Equivalent to A^..A.

<branch>@{upstream}
    The remote-tracking branch that <branch> tracks. Often abbreviated @{u}.

@{-1}
    The previous branch you were on. Same as "git switch -".

EXAMPLES IN PLAIN ENGLISH:
    git log main..HEAD
        "Show commits I've made on this branch that aren't on main."

    git log HEAD..main
        "Show commits on main that I'm missing on this branch."

    git diff origin/main..HEAD
        "What does my branch change vs origin's main?"

    git log -- README.md
        "History of just README.md."

    git log main..feature -- README.md
        "Commits on feature (not main) that touched README.md."


================================================================================
12. REMOTES (ESPECIALLY FORK WORKFLOW)
================================================================================

git remote -v
    List all remotes with their URLs.

git remote add <name> <url>
    Register a new remote. Most common:
        git remote add upstream git@gitlab.com:original/repo.git

git remote remove <name>
    Unregister a remote.

git remote rename <old> <new>
    Rename a remote.

git remote set-url <name> <new-url>
    Change a remote's URL (e.g., HTTPS → SSH).

FORK WORKFLOW CONVENTIONS:
    origin   = YOUR fork (you push here)
    upstream = the ORIGINAL repo (you pull from here)

    Sync your fork's main with upstream:
        git switch main
        git fetch upstream
        git pull --ff-only upstream main
        git push                                # push to your fork's main

    Update a feature branch with new upstream changes (rebase style):
        git fetch upstream
        git rebase upstream/main
        git push --force-with-lease


================================================================================
13. PUSH SAFETY
================================================================================

git push
    Standard push. Refuses if remote has commits you don't have.

git push -u origin <branch>
    First-time push of a new branch. -u sets upstream tracking.

git push --force
    DANGEROUS. Overwrites the remote branch even if others have pushed to it.
    Almost never use this.

git push --force-with-lease
    SAFER force push. Refuses if the remote has changed since your last fetch.
    Use this whenever you push a rebased branch.

git push origin :branch                 (or --delete branch)
    Delete the remote branch.


================================================================================
14. DETACHED HEAD
================================================================================

git checkout <commit-hash>          (or "git switch --detach <hash>")
    Goes to a specific commit not on any branch. You're now in "detached
    HEAD" state — any commits you make won't belong to a branch and can
    be lost.

WHEN YOU'RE STUCK IN DETACHED HEAD AND HAVE COMMITS:
    git switch -c rescue-branch
        → creates a branch from your current commit, saving your work.

WHEN YOU'RE STUCK IN DETACHED HEAD AND DON'T CARE:
    git switch main
        → goes back to main, abandons any commits you made (recoverable
          via reflog for ~30 days).

15. .gitignore PATTERNS
================================================================================

*.log
    Ignore all files ending in .log.

build/
    Ignore the entire "build" folder (and everything in it).

.DS_Store
    Ignore macOS junk files.

target/
    Maven build output.

!important.log
    EXCEPTION — track this file even though *.log is ignored.

NOTES:
    - .gitignore only affects UNTRACKED files. If a file is already tracked,
      adding it to .gitignore won't ignore it.
    - To start ignoring an already-tracked file:
        git rm --cached <file>
        # then add to .gitignore and commit

16. GITLAB-SPECIFIC THINGS (FROM LECTURE 5)
================================================================================

PROTECTED BRANCHES:
    Project → Settings → Repository → Protected branches
    Set main:
        - Allowed to push: Maintainers (or No one)
        - Allowed to merge: Developers + Maintainers
        - Force push: disabled
    Test it: try git push origin main as a Developer → should be rejected.

MR TEMPLATE:
    File path: .gitlab/merge_request_templates/Default.md
    Auto-loaded into the description box of every new MR.
    Multiple templates? Pick from the dropdown when opening an MR.

MINIMAL .gitlab-ci.yml:
    stages:
      - validate

    validate:
      stage: validate
      script:
        - echo "CI is running"

    File MUST be at repo root, MUST be valid YAML (2-space indent, no tabs).

FORK FROM UI:
    Repo page → Fork button → choose destination namespace.
    The fork has its own URL but Git remembers the parent.

AUTO-CLOSE ISSUE FROM MR:
    Put "Closes #N" or "Fixes #N" in the MR description.
    When the MR is merged into the default branch, the issue auto-closes.

GROUPS AS TEAMS:
    Top-nav → Groups → New group.
    Mention them in MR descriptions like @devops, @qa.

17. COMMIT MESSAGE CONVENTIONS (CONVENTIONAL COMMITS)
================================================================================

Format:
    <type>: <short description>

Common types:
    feat:     a new feature
    fix:      a bug fix
    docs:     documentation only
    chore:    tooling, dependencies, no production code change
    refactor: code change that doesn't add features or fix bugs
    test:     adding or fixing tests
    ci:       CI/CD config changes
    style:    whitespace, formatting (no logic change)
    build:    build system, Maven, Jenkins, packaging
    infra:    Puppet, server configuration, systemd

Examples:
    docs: add README
    chore: add gitignore
    feat: add login page
    fix: handle empty config
    ci: add minimal pipeline
    build: maven stable jar, jenkins publish+deploy
    infra: add Puppet configuration and infra apply pipeline

18. QUICK PROBLEM → COMMAND LOOKUP
================================================================================

GIT
"I edited a file but want to throw it away"           → git restore <file>
"I staged a file but want to unstage it"              → git restore --staged <file>
"I committed but didn't push, want to undo"           → git reset --mixed HEAD~1
"I committed AND pushed, want to undo"                → git revert HEAD
"I want to redo the last commit message"              → git commit --amend -m "new"
"I'm in detached HEAD with commits I want to keep"    → git switch -c rescue
"I lost a commit completely"                          → git reflog → find SHA → git switch -c saved <sha>
"I want my branch up to date with main (clean)"       → git fetch && git rebase origin/main
"I want my branch up to date with main (safe)"        → git fetch && git merge origin/main
"I'm working on the wrong branch"                     → git stash → git switch right-branch → git stash pop
"I forgot what I changed"                             → git status, git diff
"I want to see what's on my branch vs main"           → git log main..HEAD
"I want to see what main has that I don't"            → git log HEAD..main
"There's a conflict and I want my version"            → git checkout --ours <file>
"There's a conflict and I want their version"         → git checkout --theirs <file>
"I want to delete junk untracked files"               → git clean -n (preview) → git clean -f
"Someone pushed to my branch while I rebased"         → git push --force-with-lease
"main moved while I worked"                           → git fetch && git rebase origin/main

GITLAB CI
"I want CI to run only on MRs"                        → rules: - if: $CI_PIPELINE_SOURCE == "merge_request_event"
"I want a job only on tags"                           → rules: - if: $CI_COMMIT_TAG
"I want a job only on main pushes"                    → rules: - if: $CI_COMMIT_BRANCH == "main"
"I want a manual human gate"                          → when: manual (under the job)
"I want to keep build outputs"                        → artifacts: paths: [out/version.txt]
"I want to see the branch/tag name in my job"         → $CI_COMMIT_REF_NAME
"I want to see the commit SHA"                        → $CI_COMMIT_SHA
"Pipeline fails on grep/test — how do I read it?"     → click the job → last $ line is what failed → look at exit code

JENKINS
"Build stuck in 'Waiting for next available executor'"→ Manage Jenkins → Nodes → built-in → # executors = 1
"Checkout fails with master"                          → Job → Configure → Branch Specifier = */main
"/tmp below threshold warning"                        → drop-in: /etc/systemd/system/tmp.mount.d/override.conf size=2G
"Jenkinsfile parse error"                             → remove # comments (use //), no stray 'EOF'
"Want to keep only last N builds"                     → Job → Configure → Discard old builds → keep 10
"Want a build timeout"                                → options { timeout(time: 10, unit: 'MINUTES') }
"Want JUnit reports visible"                          → junit 'target/surefire-reports/*.xml'
"Want to keep the jar as downloadable artifact"       → archiveArtifacts artifacts: 'target/health-service.jar'
"sudo: jenkins is not allowed"                        → visudo: add NOPASSWD for the EXACT command paths
"Service didn't restart after deploy"                 → sudo journalctl -u <service> -n 100 --no-pager

MAVEN
"Jar gets a version-suffixed name"                    → <build><finalName>health-service</finalName></build>
"Tests not running in CI"                             → check target/surefire-reports/*.xml exists; junit needs it
"Want full clean build in CI"                         → mvn -B clean test package
"Compile error: release not supported"                → install openjdk-21-jdk (javac required, not just JRE)

PUPPET
"Restart service only when config changed"            → exec { refreshonly => true, subscribe => File[...] }
"Don't restart if the jar isn't there yet"            → onlyif => '/usr/bin/test -f /opt/app/app.jar'
"Need systemctl daemon-reload after unit change"      → exec { 'systemd-daemon-reload', refreshonly, subscribe => File[unit] }
"jenkins can't run puppet apply"                      → visudo: jenkins ALL=(root) NOPASSWD: /usr/bin/puppet

19. THE CANONICAL WORKFLOWS (MEMORIZE THESE)
================================================================================

A) GIT FEATURE-BRANCH WORKFLOW (any project)

# 1. Start from up-to-date main
git switch main
git pull --ff-only

# 2. Branch off
git switch -c feature/<topic>

# 3. Work in small commits
# ... edit files ...
git add <file>
git commit -m "feat: short description"

# 4. Push
git push -u origin feature/<topic>

# 5. (GitLab UI) Open a Merge Request

# 6. If main moves while your MR is open:
git fetch origin
git rebase origin/main           # OR: git merge origin/main
git push --force-with-lease      # only needed if you rebased

# 7. (GitLab UI) Squash merge, delete source branch

# 8. Clean up locally
git switch main
git pull --ff-only
git branch -d feature/<topic>


B) APP DELIVERY WORKFLOW (CI + CD, Jenkins + Maven + systemd)

Trigger: app code change.
Pipeline: app-pipeline (Jenkinsfile in vc-ci-app).

# Developer (local)
git switch -c feature/<topic>
# edit code, run mvn -B clean test package locally to confirm
git push -u origin feature/<topic>
# GitLab UI: open MR

# Jenkins (automatic on MR / on main push)
# stage Checkout       → checkout scm
# stage Build & Test   → mvn -B clean test package
# stage Publish        → junit + archiveArtifacts target/health-service.jar
# stage Deploy (CD)    → sudo cp jar; sudo systemctl restart health-service
# stage Smoke Test     → curl /health → expect HTTP 200

# Verify
sudo systemctl status health-service --no-pager
curl -fsS http://localhost:8081/health


C) INFRASTRUCTURE WORKFLOW (Puppet + Jenkins, separate repo)

Trigger: Puppet/infra code change (e.g., new env var, new package, new unit file).
Pipeline: infra-apply (Jenkinsfile in vc-ci-infra).

# Developer (local)
git switch -c feature/infra-<change>
# edit Puppet manifest under infra/puppet/environments/production/modules/profile/...
git push -u origin feature/infra-<change>
# GitLab UI: open MR

# Jenkins (infra-apply)
# stage Checkout
# stage Apply infrastructure → sudo puppet apply --modulepath=modules manifests/site.pp
# stage Verify infrastructure → test files/dirs exist; systemctl is-enabled

# Two-pipeline operating logic:
#   app code changed       → run app-pipeline
#   infra/Puppet changed   → run infra-apply

20. LAST-MINUTE BRAIN-DUMP (EXAM ESSENTIALS)
================================================================================

GIT — three places where work lives:
    Working tree  → your edited files on disk
    Index/Staging → "git add" puts files here, ready to commit
    Repository    → "git commit" puts staged files here permanently

GIT — three places work can come FROM:
    Local repo  → your machine
    origin      → your remote (usually your fork or your repo)
    upstream    → the source repo (in fork workflow)

GIT — local-only operations (never affect remote):
    git add, git commit, git stash, git branch, git tag (until pushed),
    git reset, git rebase (until pushed), git switch, git restore

GIT — operations that touch remote:
    git push, git pull, git fetch, git clone

GIT — operations that REWRITE history (dangerous on shared branches):
    git commit --amend, git rebase, git reset --hard, git push --force

GIT — operations that ADD to history (always safe):
    git commit, git merge, git revert, git tag

GITLAB CI — the four triggers you must recognize in rules:
    $CI_PIPELINE_SOURCE == "push"               → branch push
    $CI_PIPELINE_SOURCE == "merge_request_event" → MR pipeline
    $CI_COMMIT_TAG                              → tag pipeline
    $CI_COMMIT_BRANCH == "main"                 → main pushes only

JENKINS — three pipeline anatomy parts:
    pipeline { agent any; options{...}; environment{...}; stages{...}; post{...} }
        agent any        → run on any node (the controller in single-VM lab)
        options          → timeout, log rotation, etc.
        environment      → env vars exposed to every step
        stages           → ordered list of stage{}; each has steps{}
        post             → blocks always{}, success{}, failure{}, run after stages

MAVEN — three commands that matter for the exam:
    mvn -B clean test package
    -B    → batch mode (no prompts, clean log)
    clean → wipe target/
    test  → compile, run unit tests (produces surefire-reports XML)
    package → assemble the artifact (target/<finalName>.jar)

SYSTEMD CD — three files you'll touch on the VM:
    /etc/systemd/system/health-service.service   → unit file
    /etc/health-service.env                      → runtime env vars
    /opt/health-service/app.jar                  → the deployed jar
After unit changes: sudo systemctl daemon-reload, then restart.

PUPPET — three resource types and four ordering metaparams:
    Resources:     package, file, service, exec
    Ordering:      require, before, notify, subscribe
    refreshonly:   only run when notified (Exec only)

TWO-PIPELINE SEPARATION — the rule of thumb:
    App pipeline ships SOFTWARE (jar, restart, smoke test).
    Infra pipeline brings the MACHINE to desired state (packages, paths,
    env files, systemd units).
    Mixing them = sysadmin knowledge in the app pipeline. Splitting them =
    each repo reviewable by the right team.

21. GITLAB CI/CD PIPELINES (.gitlab-ci.yml) — POST-MIDTERM L1+L2
================================================================================

WHERE IT LIVES:
    Repo root, filename exactly .gitlab-ci.yml. YAML, 2-space indent, NO TABS.

MINIMAL PIPELINE (one stage, one job):
    stages:
      - validate

    validate:
      stage: validate
      script:
        - echo "CI is running"

ANATOMY:
    stages: ordered list of phases. Jobs in the same stage run in parallel;
            later stages start only after earlier ones pass.
    <job_name>: a job. Has a stage and a script:
        stage: <name from stages>
        script: a list of shell commands

EXAMPLE — TWO STAGES, A POLICY GATE:
    stages:
      - validate
      - policy

    validate:
      stage: validate
      script:
        - echo "Pipeline ref name: $CI_COMMIT_REF_NAME"
        - echo "Commit SHA: $CI_COMMIT_SHA"
        - ls -la

    policy_check:
      stage: policy
      script:
        - test -f README.md
        - grep -q "CI_GATE_OK" README.md     # fails if not found

PREDEFINED CI VARIABLES (the ones you'll actually use):
    $CI_COMMIT_REF_NAME    branch name OR tag name (whichever this pipeline is on)
    $CI_COMMIT_SHA         full commit hash
    $CI_COMMIT_TAG         set only on tag pipelines (great in rules)
    $CI_COMMIT_BRANCH      branch name (NOT set on tag pipelines)
    $CI_PIPELINE_SOURCE    "push" | "merge_request_event" | "schedule" | "web" | ...
    $CI_PROJECT_DIR        absolute path to checked-out repo inside the runner
    $CI_JOB_NAME           current job name (handy in echoes)

rules: — THE NEW WAY TO CONTROL WHEN A JOB RUNS
    rules is a list. Evaluated TOP-DOWN, FIRST MATCH WINS. Each entry can have:
        if:        a string expression to test (compared as strings)
        when:      "always" (default) | "manual" | "never" | "on_success" | "on_failure"
        changes:   list of file globs — run only if any matched file changed
        exists:    list of file globs — run only if any matched file exists

    Run only on MR pipelines:
        rules:
          - if: $CI_PIPELINE_SOURCE == "merge_request_event"

    Run only on tags:
        rules:
          - if: $CI_COMMIT_TAG

    Run only on main pushes:
        rules:
          - if: $CI_COMMIT_BRANCH == "main"

    Manual gate (button in UI):
        rules:
          - if: $CI_COMMIT_TAG
        when: manual

    Explicitly never on tags:
        rules:
          - if: $CI_COMMIT_TAG
            when: never
          - when: always

artifacts: — KEEP FILES BETWEEN JOBS AND AS BUILD OUTPUT
    package_release:
      stage: release
      script:
        - mkdir -p out
        - echo "$CI_COMMIT_TAG" > out/version.txt
      artifacts:
        paths:
          - out/version.txt

    Artifacts are:
      - downloadable from the job page in the GitLab UI
      - available to LATER stages' jobs in the same pipeline
      - kept for the project's artifact retention period

THE THREE CI MODELS YOU MUST KNOW:
    Model A — MR validation:        rules: if: $CI_PIPELINE_SOURCE == "merge_request_event"
    Model B — Branch push pipeline: default (no rules; just runs on push)
    Model C — Tag/release pipeline: rules: if: $CI_COMMIT_TAG
    + manual gate on top of C:      add when: manual to the job

STAGED DESIGN (fast first, slow later):
    stages: [fast, slow, release]
    - fast jobs: lint, unit (every push, every MR)
    - slow jobs: integration, security (MR only — too slow for every push)
    - release jobs: package, deploy (tags only)

WHY USE STAGES THIS WAY:
    - Don't waste CI minutes running 10-minute scans on every typo-fix push.
    - Always-green fast jobs give devs immediate feedback.
    - Slow jobs gate MRs (the human review moment).
    - Release jobs gate tags (the production moment).

WHY TAGS FOR RELEASES (one-liner for the exam):
    Tags are immutable refs. v0.7 always points to the exact same commit, so
    CI can rebuild the same release forever. Branches keep moving.

COMMON .gitlab-ci.yml MISTAKES:
    - Tabs instead of 2 spaces (YAML errors out).
    - Missing colon after stage name.
    - File not at repo root.
    - Job references a stage not declared in stages:.
    - rules: vs only:/except: — only/except are legacy; use rules.
    - Forgetting when: manual sits at the JOB level, not inside rules entries
      (it can be inside too, but the simpler placement is the job).

THREE COMMON RUNTIME BLOCKERS YOU MUST FIX:

A) BUILD STUCK IN "Waiting for next available executor"
    Cause: controller has 0 executors or asks for a label that doesn't exist.
    Fix:
        Manage Jenkins → Nodes → built-in node → Configure
        # of executors = 1
    Also: in Jenkinsfile use `agent any` (no label).

B) "/tmp below threshold" WARNING
    Default Ubuntu tmpfs /tmp is ~953 MB; Jenkins wants ≥ 1 GiB. Resize to 2 G:
        sudo mkdir -p /etc/systemd/system/tmp.mount.d
        sudo tee /etc/systemd/system/tmp.mount.d/override.conf > /dev/null <<'EOF'
        [Mount]
        What=tmpfs
        Where=/tmp
        Type=tmpfs
        Options=mode=1777,nosuid,nodev,size=2G
        EOF
        sudo systemctl daemon-reload
        sudo systemctl restart tmp.mount
        df -h /tmp                          # confirms 2.0G

C) SWAP = 0 GB
    Random OOM kills during plugin installs / Maven builds. Create 2 G swap:
        sudo fallocate -l 2G /swapfile
        sudo chmod 600 /swapfile
        sudo mkswap /swapfile
        sudo swapon /swapfile
        echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
        swapon --show && free -h

    Manage Jenkins → Plugins → Installed
    Required: Pipeline, Git, Credentials
    If missing: install only the missing one, restart if prompted.

LIMIT BUILD HISTORY (stops disk filling up over weeks):
    Job → Configure → Discard old builds → keep 10
    (Or set programmatically in Jenkinsfile via buildDiscarder, see §23.)

GITLAB CREDENTIAL (HTTPS + Personal Access Token):
    GitLab: Edit Profile → Access Tokens → scope read_repository → create
    Jenkins: Manage Jenkins → Credentials → (global) → Add Credentials
        Kind: Username with password
        Username: <gitlab username>
        Password: <the PAT>
        ID: gitlab-pat        (recommended; you'll reference this in jobs)

CREATE A PIPELINE JOB (Pipeline script from SCM):
    New Item → Pipeline → name app-pipeline
    Pipeline definition: Pipeline script from SCM
    SCM: Git
    Repository URL: https://gitlab.com/<ns>/<repo>.git
    Credentials: gitlab-pat
    Branch Specifier: */main           ← NOT */master
    Script Path: Jenkinsfile
    Save → Build Now

WHERE WORKSPACES ARE ON DISK:
    /var/lib/jenkins/workspace/<job-name>/

SUDOERS FOR JENKINS (lab-only, NARROW SCOPE):

23. JENKINSFILE (DECLARATIVE PIPELINE SYNTAX) — POST-MIDTERM L3+L4
================================================================================

WHERE IT LIVES:
    Repo root, filename Jenkinsfile (no extension). Groovy syntax.

MINIMAL PIPELINE:
    pipeline {
      agent any
      stages {
        stage('Info') {
          steps {
            sh 'echo "Branch: ${BRANCH_NAME}"'
            sh 'git --version'
            sh 'ls -la'
          }
        }
      }
    }

TOP-LEVEL BLOCKS:
    pipeline { ... }     wraps everything
      agent any          → run on any available agent (your controller in single-VM lab)
      options { ... }    → build-time settings (timeout, log rotation)
      environment { ... }→ env vars exposed to every sh step
      stages { ... }     → ordered list of stage blocks
      post { ... }       → always{}, success{}, failure{}, unstable{}, changed{}

OPTIONS (the two you'll use):
    options {
      timeout(time: 20, unit: 'MINUTES')        # kill build if it runs longer
      buildDiscarder(logRotator(numToKeepStr: '10'))   # keep last 10 builds
    }

ENVIRONMENT:
    environment {
      APP_PORT = "8081"
      STUDENT_NAME = "Your Name"
    }
    # use as $APP_PORT inside sh '...', or ${APP_PORT} inside sh """..."""

STAGES — THE FIVE STANDARD ONES FOR APP DELIVERY:
    stage('Checkout')         { steps { checkout scm } }
    stage('Build & Test')     { steps { sh 'mvn -B clean test package' } }
    stage('Publish')          { steps {
                                  junit 'target/surefire-reports/*.xml'
                                  archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
                                } }
    stage('Deploy (CD)')      { steps {
                                  sh '''
                                    set -e
                                    sudo cp target/health-service.jar /opt/health-service/app.jar
                                    sudo systemctl restart health-service
                                    sleep 2
                                  '''
                                } }
    stage('Smoke Test')       { steps {
                                  sh '''
                                    set -e
                                    code=$(curl -s -o /dev/null -w "%{http_code}" "http://localhost:${APP_PORT}/health")
                                    [ "$code" = "200" ]
                                  '''
                                } }

STEPS (the keywords inside a steps{} block):
    sh '...'                     → run a single shell command
    sh '''multi
        line
        script'''                → multiline shell (use set -e for fail-fast)
    checkout scm                 → check out the same repo the Jenkinsfile came from
    junit '<glob>'               → collect JUnit XML, show test trend on the job
    archiveArtifacts artifacts: '<glob>', fingerprint: true
                                 → save files as downloadable build artifacts
    sleep <n>                    → wait n seconds (use for "let the service boot")
    timeout(...) { ... }         → bounded sub-block
    retry(<n>) { ... }           → retry the block on failure

POST CONDITIONS:
    post {
      always   { archiveArtifacts artifacts: 'out/**', fingerprint: true }
      success  { echo 'Pipeline succeeded' }
      failure  { echo 'Pipeline failed' }
      unstable { echo 'Tests failed but build itself was OK' }
      changed  { echo 'Status changed from last build' }
    }

SHELL CONVENTIONS INSIDE sh:
    - Start multi-line shell with `set -e` so the stage fails on the first error.
    - For interpolated env vars: double-quoted string "..." or """..."""
      sees Groovy variables and env (${APP_PORT}). Single-quoted '...' sees
      raw shell vars only ($APP_PORT) — usually what you want for safety.

COMMENTS:
    # is NOT a Jenkinsfile comment at the top level — that breaks the parse.
    Use // single-line or /* block */ in Groovy.
    Inside an sh '''...''' block, normal shell # comments are fine.

FIVE COMMON JENKINSFILE PROBLEMS (FROM THE LABS):
    1. Branch Specifier was */master in the job config → checkout fails.
       Fix: */main.
    2. # comment at Jenkinsfile top level → parse error.
       Fix: use //.
    3. archiveArtifacts path doesn't match what stages produced (e.g., wrong
       version-suffixed jar name) → "No artifacts found".
       Fix: set <finalName> in pom.xml (see §24), match the exact path.
    4. sudo commands not allowed → "jenkins is not allowed".
       Fix: visudo with exact paths (see §22).
    5. Build hangs forever → 0 executors on the controller.
       Fix: Manage Jenkins → Nodes → built-in → # of executors = 1.

24. MAVEN LIFECYCLE FOR CI — POST-MIDTERM L4
================================================================================

INSTALL ON THE VM:
    sudo apt-get install -y openjdk-21-jdk maven
    mvn -version       # confirms

THE ONE COMMAND THAT BUILDS, TESTS, AND PACKAGES:
    mvn -B clean test package

WHAT EACH WORD DOES:
    -B (batch mode)
        Non-interactive, cleaner progress output. Always use in CI.
    clean
        Runs the `clean` lifecycle. Deletes target/.
        Why: ensure you're not picking up old class files / artifacts.
    test
        Runs the `default` lifecycle UP TO phase `test`. That's:
            validate    → sanity checks
            compile     → target/classes/
            test-compile→ target/test-classes/
            test        → run unit tests
        Produces: target/surefire-reports/*.xml (JUnit XML, picked up by Jenkins).
    package
        Continues the default lifecycle through `package`.
        Produces: target/<artifactId>-<version>.jar by default.

STABLE JAR NAMING (so CD doesn't have to guess the filename):
    <build>
      <finalName>health-service</finalName>
      <plugins>
        ...
      </plugins>
    </build>

    Without finalName: target/health-service-0.1.0-SNAPSHOT.jar
    With finalName:    target/health-service.jar      ← much easier in Jenkinsfile

MAIN CLASS IN THE JAR MANIFEST (so `java -jar foo.jar` knows what to run):
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-jar-plugin</artifactId>
      <version>3.4.2</version>
      <configuration>
        <archive>
          <manifest>
            <mainClass>com.vcci.HealthServer</mainClass>
          </manifest>
        </archive>
      </configuration>
    </plugin>

JUNIT 5 IN MAVEN (test dependency + surefire plugin):
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.10.2</version>
      <scope>test</scope>
    </dependency>

    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
      <version>3.2.5</version>
      <configuration>
        <useModulePath>false</useModulePath>     <!-- avoid module-path issues -->
      </configuration>
    </plugin>

WHERE OUTPUTS LAND (memorize these paths):
    target/                        the whole build output
    target/classes/                compiled main code
    target/test-classes/           compiled tests
    target/surefire-reports/*.xml  JUnit results (Jenkins `junit` step picks up)
    target/<finalName>.jar         the jar (if finalName set)

RUNNING MAVEN AS THE JENKINS USER (when debugging on the VM):
    sudo -u jenkins -H bash -lc 'mvn -B clean test package'

WRITING A REAL TEST (replace assertTrue(true)):
    package com.vcci;
    import org.junit.jupiter.api.Test;
    import static org.junit.jupiter.api.Assertions.assertTrue;

    class MessageBuilderTest {
      @Test void rootMessageContainsName() {
        String msg = MessageBuilder.rootMessage("Your Name");
        assertTrue(msg.contains("Your Name"));
      }
    }

COMMON MAVEN PROBLEMS IN CI:
    - "release version 21 not supported" → need openjdk-21-jdk (JRE alone is
      missing javac). The JRE runs java; the JDK provides the compiler.
    - "no tests were executed" → surefire-plugin <useModulePath>false</useModulePath>
      fixes the common module-path mismatch with junit-jupiter.
    - Wrong jar name in Jenkinsfile → either set <finalName> or list the exact
      versioned filename in archiveArtifacts.

25. CONTINUOUS DELIVERY ON LINUX (systemd) — POST-MIDTERM L3+L4
================================================================================

PATTERN: keep the deployed app running as a systemd service. Jenkins CD just
copies a new jar and restarts the service. Systemd handles boot, restart, logs.

THREE FILES THAT DEFINE THE DEPLOY TARGET:
    /etc/systemd/system/<name>.service     unit file (the service definition)
    /etc/<name>.env                        runtime environment variables
    /opt/<name>/app.jar                    the actual jar deployed by CI

UNIT FILE TEMPLATE (Type=simple, restart-on-failure, env file):
    [Unit]
    Description=Health Service (training)
    After=network.target

    [Service]
    Type=simple
    WorkingDirectory=/opt/health-service
    EnvironmentFile=-/etc/health-service.env   # leading '-' = ignore if missing
    ExecStart=/usr/bin/java -jar /opt/health-service/app.jar
    Restart=always
    RestartSec=2

    [Install]
    WantedBy=multi-user.target

INSTALL / ENABLE / VERIFY:
    sudo systemctl daemon-reload          # always after editing a unit file
    sudo systemctl enable health-service  # auto-start on boot
    sudo systemctl start health-service
    sudo systemctl status health-service --no-pager
    sudo systemctl is-enabled health-service   # prints "enabled"

LOGS:
    sudo journalctl -u health-service -n 100 --no-pager   # last 100 lines
    sudo journalctl -u health-service -f                  # follow live

WHEN TO daemon-reload:
    Only after the .service file itself changes. After daemon-reload, you still
    need to restart the service for the new unit to take effect.

ENV FILE (referenced by EnvironmentFile=):
    APP_PORT=8081
    STUDENT_NAME=Your Name

    Created in CI like this:
        printf "APP_PORT=%s\nSTUDENT_NAME=%s\n" "$APP_PORT" "$STUDENT_NAME" \
          | sudo tee /etc/health-service.env > /dev/null

DEPLOY STAGE (the four shell lines you'll memorize):
    sudo tee /etc/health-service.env >/dev/null <<EOF    # 1. write env
APP_PORT=$APP_PORT
STUDENT_NAME=$STUDENT_NAME
EOF
    sudo cp target/health-service.jar /opt/health-service/app.jar   # 2. drop new jar
    sudo systemctl restart health-service                            # 3. restart
    sleep 2                                                           # 4. let it boot

SMOKE TEST PATTERN (HTTP 200 on /health):
    code=$(curl -s -o /dev/null -w "%{http_code}" "http://localhost:${APP_PORT}/health")
    [ "$code" = "200" ]

    -s   silent (no progress meter)
    -o   discard the body (we only care about status)
    -w "%{http_code}"   print just the status code
    The [ ... ] test in a CI pipeline fails the stage if code != 200.

EXACT SUDOERS RULE FOR THIS PATTERN:
    jenkins ALL=(ALL) NOPASSWD: /usr/bin/tee, /bin/cp, \
        /bin/systemctl restart health-service, \
        /bin/systemctl status health-service

THREE COMMON DEPLOY FAILURES:
    1. "sudo: jenkins is not allowed" → sudoers paths are wrong. Run
       `which systemctl` and use the exact path Jenkins is calling.
    2. "Failed to start health-service" → look at journalctl. Usually a bad
       env file, missing jar at /opt/health-service/app.jar, or port in use.
    3. Smoke test returns 000 → service didn't start in time; increase the
       sleep, or check journalctl for startup errors.

26. CONFIGURATION MANAGEMENT WITH PUPPET — POST-MIDTERM L7
================================================================================

WHY PUPPET (the separation of concerns):
    App pipeline ships SOFTWARE (jar, restart, smoke test).
    Infra pipeline brings the MACHINE to desired state (packages, directories,
    env files, systemd units).
    Two repos, two Jenkinsfiles, two pipelines.

INSTALL ON THE VM:
    sudo apt-get update -y
    sudo apt-get install -y puppet
    puppet --version

REPO LAYOUT (vc-ci-infra):
    vc-ci-infra/
      Jenkinsfile
      infra/
        puppet/
          environments/
            production/
              manifests/
                site.pp
              modules/
                role/
                  manifests/
                    app_server.pp
                profile/
                  manifests/
                    health_service.pp

APPLY THE MANIFEST:
    cd infra/puppet/environments/production
    sudo /usr/bin/puppet apply --modulepath=modules manifests/site.pp

ROLE / PROFILE PATTERN:
    site.pp         picks role(s) for the machine            (include role::app_server)
    role/           composes profiles into a machine type    (one role per server kind)
    profile/        configures ONE concept (one service, one stack)
    Don't put resources directly in roles. Roles are pure composition.

THE FOUR RESOURCE TYPES YOU WILL ACTUALLY USE:

(1) package — install OS packages:
    package { ['openjdk-21-jre-headless', 'curl']:
      ensure => installed,
    }
    Other ensure values: present (same as installed), absent, latest.

(2) file — create/manage files and directories:
    file { '/opt/health-service':
      ensure => directory,
      owner  => 'root',
      group  => 'root',
      mode   => '0755',
    }

    file { '/etc/health-service.env':
      ensure  => file,
      mode    => '0644',
      content => "APP_PORT=${app_port}\nSTUDENT_NAME=${student_name}\n",
    }

    For multiline content, use the heredoc form:
    file { '/etc/systemd/system/health-service.service':
      ensure  => file,
      mode    => '0644',
      content => @("UNIT")
        [Unit]
        Description=...
        ...
        | UNIT
    }

(3) service — manage systemd (or other init) services:
    service { 'health-service':
      enable     => true,         # auto-start on boot
      hasrestart => true,         # use the service's own restart
      require    => [
        Package['openjdk-21-jre-headless'],
        File['/opt/health-service'],
        File['/etc/systemd/system/health-service.service'],
      ],
    }
    Note: ensure => running would block until the service is up. We omit it
    here so the lab's app-pipeline (which copies the jar) can start it later.

(4) exec — run a one-off shell command (use sparingly, only when no native
            resource fits):
    exec { 'systemd-daemon-reload':
      command     => '/bin/systemctl daemon-reload',
      refreshonly => true,
      subscribe   => File['/etc/systemd/system/health-service.service'],
    }

    refreshonly => true means "only run when one of my subscribed/notified
    resources actually changed". That's how we get "daemon-reload only when
    the unit file changes" and "restart only when config changes".

    Use onlyif/unless to guard execs:
    exec { 'restart-on-config-change':
      command     => '/bin/systemctl restart health-service',
      refreshonly => true,
      onlyif      => '/usr/bin/test -f /opt/health-service/app.jar',
      subscribe   => [File['/etc/health-service.env'],
                      File['/etc/systemd/system/health-service.service']],
      require     => Exec['systemd-daemon-reload'],
    }

THE FOUR ORDERING METAPARAMETERS:
    require   => X       I depend on X being applied BEFORE me
    before    => X       X depends on me being applied BEFORE it
    notify    => X       if I change, refresh X    (PUSH; opposite of subscribe)
    subscribe => X       if X changes, refresh me  (PULL; opposite of notify)

    Two of these are "refresh" relationships (notify/subscribe); the other two
    are pure ordering (require/before).

DECLARING A PROFILE WITH PARAMETERS:
    class profile::health_service (
      Integer $app_port = 8081,
      String  $student_name = 'Student',
    ) {
      package { ... }
      file { ... }
      service { ... }
      exec { ... }
    }

    Override in site.pp via Hiera or:
        class { 'profile::health_service':
          student_name => 'Your Name',
        }

ROLE THAT INCLUDES THE PROFILE:
    class role::app_server {
      include profile::health_service
    }

site.pp ENTRY POINT:
    include role::app_server
    (Or restrict by node: node 'webvm.example.com' { include role::app_server })

INFRA-APPLY JENKINSFILE (the three stages):
    stage('Checkout')                    → checkout scm
    stage('Apply infrastructure ...')    → sudo puppet apply --modulepath=modules manifests/site.pp
    stage('Verify infrastructure')       → test -d/-f; systemctl is-enabled

SUDOERS FOR THE INFRA PIPELINE:
    jenkins ALL=(root) NOPASSWD: /usr/bin/puppet, /bin/systemctl, /usr/bin/systemctl

WHAT TO REMOVE FROM THE APP PIPELINE AFTER INTRODUCING PUPPET:
    - tee /etc/health-service.env             (Puppet owns env)
    - mkdir /opt/health-service               (Puppet owns the dir)
    - any systemd unit creation               (Puppet owns the unit)
    - systemctl daemon-reload                 (only runs when unit changes;
                                               app pipeline doesn't change it)
    The app pipeline keeps only: build, test, package, copy jar, restart, smoke.

THE TWO-PIPELINE OPERATING LOGIC (the exam-friendly version):
    | Scenario                            | Pipeline to run         |
    | App code changed                    | app-pipeline            |
    | Puppet/server config changed        | infra-apply             |
    | Fresh VM (nothing on it)            | infra-apply, THEN app   |
    | Only env/unit changed (no new jar)  | infra-apply only        |

COMMON PUPPET PROBLEMS:
    1. "Could not find class profile::health_service" → wrong --modulepath or
       wrong filename. The file MUST be at
       modules/profile/manifests/health_service.pp.
    2. Service doesn't restart after config change → forgot subscribe on the
       exec, or refreshonly is false (it MUST be true for "only on change").
    3. "Java package install fails" → image-specific Java package name. Try
       openjdk-17-jre-headless or whichever JRE is available. Match the
       version your app needs (21 for this course).
    4. Service tries to start before app.jar exists → guard the restart exec
       with onlyif => '/usr/bin/test -f /opt/.../app.jar'.
